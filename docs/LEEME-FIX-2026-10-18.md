## ⚡ PAQUETE v10 (19-oct) — MÉXICO COMPLETO en el panel de PUBLICAR PROPIEDAD

Petición: *"en mi panel para publicar una propiedad… me gustó la funcionalidad
que ya están todos los municipios o ciudades para seleccionarlas — ¿podrías

### Qué trae (mexico-ubicacion.js v1.0 — 1 archivo nuevo + 1 línea en tu página)

- **El MISMO catálogo MÉXICO COMPLETO del panel de marcas v2.6** (32 entidades,
  2,476 municipios oficiales, base INEGI 2020-2024) ahora como **widget
  universal** para cualquier formulario del sitio, en especial el panel de
  publicar propiedades.
- **Cascada Estado → Ciudad igual a la que te gustó**: al lado del campo de
  ciudad aparece un selector "Estado" (con conteos: "Jalisco (125)"); al
  elegirlo, el campo de ciudad muestra TODOS los municipios de esa entidad.
- **Detección automática**: encuentra campos llamados `ciudad`, `municipio`,
  `ubicacion.ciudad`, `direccion.ciudad`, `city`, etc. (select o input de
  texto). En inputs añade sugerencias con TODOS los municipios (datalist);
  puedes elegir estado primero para acotar la lista. También se reengancha
  solo si el formulario carga después (SPA).

  cuyas opciones son estados de México), se sincroniza en ambos sentidos: al
  elegir ciudad se completa el estado, y al cambiar estado se filtran las
  ciudades. Un "estado" tipo Nuevo/Usado/Remodelado o Activo/Inactivo se
  detecta y SE IGNORA — jamás le escribe.

### Por qué NO rompe nada (diseño a prueba de todo)

- **No borra ni reemplaza nada**: el campo de ciudad conserva su `name`, `id`
  y clases; las opciones que ya traía se PRESERVAN (aparecen como grupo
  "Otras opciones" cuando eliges estado) — los borradores guardados no se
  pierden. Si la página repinta el campo, el widget reaplica la cascada y
  además CONSERVA lo que el usuario había elegido.
- **El payload no cambia**: los valores nuevos son texto plano del municipio
  ("Guadalajara"), del mismo tipo que el sitio ya guarda. El selector de
  estado inyectado NO tiene `name` → no viaja en el formulario.
- **Opt-in para guardar el estado**: si quieres que el estado elegido se
  envíe también, añade ANTES del script:
  `<script>window.MEXICO_UBICACION = { campoEstado: 'estado' };</script>`
  (crea/mantiene un `<input type="hidden" name="estado">` con la entidad).
- **Autocuración**: si algo falla, restaura el campo original y sigue; si el
  dataset viniera corrupto, se desactiva entera. Cero red, cero dependencias,
  sin estilos inline, amigable con CSP. En las páginas de marcas NO interviene
  (el panel v2.6 ya trae su propia cascada).
- **Si no encuentra tus campos** (nombres muy distintos), lo dice en consola y
  puedes montarlo a mano:
  `MexicoUbicacion.montar({ ciudad: '#id-del-select', estado: '#id-estado' })`
  — y `MexicoUbicacion.desmontar('#id-del-select')` restaura todo.

## DIAGNÓSTICO (1 causa raíz + 2 faltantes)

### CAUSA RAÍZ del bucle de login de marcas: el monolito viejo `models.js`
Tu producción tiene **los dos** en `src/marcas/`:
- `models.js`  ← archivo viejo (monolito): `Brand.accountId` **required**
- `models/`    ← carpeta nueva que subiste (usa `cuenta`)

Node resuelve `require('./models')` **primero el ARCHIVO, después la carpeta**.
El monolito viejo SIEMPRE ganaba: tus controllers nuevos creaban la marca con
`cuenta`, el esquema viejo exigía `accountId` →

```
[marcas][autenticarMarca] Brand validation failed: accountId: Path `accountId` is required.
```
→ 401 → el panel reintenta → bucle. Además el `BrandAccount` viejo no tiene
`password`, así que el login con contraseña jamás podía funcionar.

**ARREGLO**: se entrega un `models.js` NUEVO (shim) que pisa el monolito y
re-exporta la carpeta nueva. Ya no puede haber mezcla de versiones.

### `[CORS] Origen bloqueado: https://somosvivemas.com`
El whitelist venía solo de `CLIENT_URL`. Si el `.env` no trae el dominio exacto
(o está en la variante www opuesta), el servidor bloqueaba SU PROPIO sitio.
**ARREGLO (app.js v5)**: mismo origen siempre permitido (compara contra el Host
del servidor) + normalización www↔dominio-desnudo + dominio propio como
cinturón de seguridad. Funciona aunque `CLIENT_URL` esté vacía.

### `GET /api/admin/salud` 500 y `GET /api/admin/marcas` 500
- `/api/admin/marcas` usaba el esquema viejo → `populate()` sobre paths que no
  existen → crash. **Lo cura el shim + Brand.js v4** (además ahora el schema
  trae `strictPopulate: false`: un populate desalineado se ignora, no 500).
- `/api/admin/salud`: app.js v5 registra una ruta de salud **defensiva** antes
  del montaje `/api/admin` — responde 200 siempre, con conteos best-effort.

### `GET /api/herramientas/ciudades-disponibles` 404
La calculadora llama un endpoint que el backend nunca registró. **ARREGLO**:
nuevo `src/routes/herramientas.routes.js` montado en app.js v5. Devuelve las
ciudades de propiedades aprobadas (con total real por ciudad) y, si aún no hay,
el catálogo del directorio. Nunca 500.
